# Schema and sample data: TBox and ABox, kept apart

*An ontology says what kinds of things exist and how they relate. Data says which particular things exist. This project keeps the two in different files, and this chapter explains why that matters more than it first appears.*

## 1. Two kinds of statement

Compare two sentences about a hospital:

1. "A **Patient** is a kind of **Person**, and a Patient can have **Encounters**."
2. "**John Doe** is a Patient, born on 14 March 1985, and he had **Encounter001** on 1 March 2026."

The first is about *kinds*. It would be equally true in any hospital. The second is about *this* hospital's particular people and events, and it changes every day.

Ontology engineers have names for them:

| Name | Short for | Plain meaning | In this project |
|---|---|---|---|
| **TBox** | terminology box | The vocabulary and rules: classes, properties, hierarchies, definitions | **the schema**, `ontology/healthcare_schema.ttl` |
| **ABox** | assertion box | The facts about particular individuals | **the sample data**, `data/sample_data.ttl` |

You will also hear "schema" and "instance data". They mean the same thing.

## 2. The layout

```text
ontology/healthcare_schema.ttl   the schema (TBox) + the controlled vocabularies   generated by scripts/generate_hc_ontology.py
shapes/*.ttl                     the rules for valid data (SHACL)                    written by hand
data/source/*.csv                the raw synthetic records                           written by hand
data/sample_data.ttl             the instance data (ABox), built from the CSVs        generated by scripts/generate_sample_data.py
sparql/*.rq                      the competency questions (the "queries" directory)   written by hand
core/dataset.py                  the union of schema + data, which everything reads
```

Four things are kept separate on purpose: what exists *in principle* (schema), what counts as *valid* (shapes), what exists *in this sample* (data), and what we *ask* (queries). Each changes for a different reason, at a different speed, and is reviewed by a different kind of person.

## 3. Why separate them

**They change at different rates.** The schema changes when the *model* changes: a new class, a new property. That is a design decision, reviewed carefully. The data changes whenever there is a new record. When both live in one file, every new patient is a change to "the ontology", and a reviewer cannot tell a model change from a data change in a diff.

**They are owned by different people.** A clinician or data steward edits records. An ontology engineer edits the schema. Separate files mean separate responsibility, separate review and separate history.

**One schema serves many datasets.** The same schema can describe this synthetic sample, a test fixture, or (elsewhere) a real hospital's data that must never be committed to a repository. Real data cannot live inside the ontology file. With the separation, the schema is publishable and the data is not, and nothing about that needs special handling.

**The schema should be small enough to read.** A reader can open `healthcare_schema.ttl` and see the model without wading through patients.

**A test can prove the boundary.** If synthetic people drift into the schema, a test fails. When both live in one file, "is this a model fact or a data fact?" is a question only a human can answer.

**It mirrors how the tools work.** SHACL validates *data* against *shapes*. A reasoner draws conclusions about data using the schema. A projection copies data into a graph database. Each wants to know which part is which.

## 4. A subtle case: the controlled vocabularies

The schema contains 30 *individuals*, which seems to break the rule. They are the controlled vocabularies: the 11 specialties, 4 genders, 4 encounter types, 7 medication categories and their 4 schemes.

They belong in the schema because the schema's own definitions depend on them. The defined class `AntidiabeticMedication` is written as "a Medication whose category is *the Antidiabetic category*". That points at an individual (`MedCategoryAntidiabetic`), so the individual must exist wherever the definition does. They are also not synthetic: they describe the model's vocabulary, not any particular patient.

The rule the tests enforce is therefore precise: *the schema may contain individuals only if they are vocabulary concepts or schemes.* `Metformin` (a particular drug in a particular hospital's formulary) is data. `MedCategoryAntidiabetic` (a category the ontology defines) is schema.

## 5. How the pieces combine

```text
 ontology/healthcare_schema.ttl ----+
                                    +--> Dataset.graph() --> SHACL  --> reasoner --> SPARQL --> projection to Neo4j
 data/sample_data.ttl --------------+          (one merged RDF graph)
```

`core/dataset.py` loads both files into one RDF graph. Merging graphs in RDF is just taking the union of their triples, because every statement stands alone; there is nothing to reconcile. The instance IRIs use the schema's namespace (`http://example.org/healthcare-hospital.owl#PatientJohn`), so the data refers to the schema's terms directly and every IRI that existed before the split is unchanged.

The data file has its own small header, a second `owl:Ontology` that `owl:imports` the schema. That records, in the data itself, which schema it is written in terms of.

Consumers: SHACL validation (`ShaclValidator.validate_ontology`), SPARQL (`HealthcareOntology.execute_sparql`, run in a bounded worker), the OWL reasoner (it receives the merged graph without the header, so it never tries to fetch the import over the network), the property-graph projection, and the API's object model. A tool that needs a single RDF/XML document gets one built in memory; no combined file is stored.

Neo4j is unchanged in role: it is a **derived** projection of the combined graph. The projection built from schema + data is identical, fingerprint for fingerprint, to the one built from the old single file (`PROJECTION_FINGERPRINT` in `tests/test_schema_and_data.py`).

## 6. Generation

Two generators, two responsibilities:

| | `scripts/generate_hc_ontology.py` | `scripts/generate_sample_data.py` |
|---|---|---|
| Builds | the schema and vocabularies | the individuals |
| Reads | `services/reference_vocab.py` | `data/source/*.csv`, the drug reference |
| Checks first | that nothing but vocabulary individuals is in the schema | the **data contract** on the CSVs |
| Gate before writing | SHACL on the schema | SHACL on schema + data **together** |
| Writes | `ontology/healthcare_schema.ttl` | `data/sample_data.ttl` |

Both write deterministic Turtle (blank nodes are canonicalised, output is sorted), atomically, so a failed run leaves the previous file untouched and an unchanged input gives byte-identical output.

```bash
python scripts/generate_hc_ontology.py     # the schema
python scripts/generate_sample_data.py     # the sample data (needs the schema)
python scripts/validate.py                 # checks both, and their combination
```

The sample-data generator reuses the schema module's classes and properties to create individuals, but stores them in a *separate* Owlready2 ontology whose individuals live in the schema's namespace. That is why the data file contains instances and nothing else.

## 7. Validation

```text
data contract (CSV)  ->  build individuals  ->  schema + data  ->  SHACL  ->  write data/sample_data.ttl
                                                       |
                                                       +--> reasoner (where required) --> projection
```

`scripts/validate.py` now checks, in order: the CSV contract; that schema and data each parse and the schema holds no instances; that each committed file equals its generator's output; SHACL on the **combined** graph; the projection plan; optionally the reasoner. The sample data alone is deliberately *not* valid by itself (20 SHACL violations), because the shapes need the schema's class hierarchy to recognise the data; a test shows this.

## 8. Running on the schema alone

Set `SAMPLE_DATA_FILE=` (empty) and the platform runs with no instances at all: the ontology service answers, the projection contains only the vocabularies, SPARQL returns nothing for patients. This is how you would deploy the model without the synthetic data. It is also a good way to see the separation: the schema is a complete ontology with zero patients.

## 9. Trade-offs and common mistakes

**Trade-offs.** Two files to keep in step: the data must be generated against the schema that is current (the generator checks this by validating the combination). A reader opening one file sees half the picture. Merging costs a parse of two files instead of one. The runtime object model (Owlready2) cannot read Turtle, so it is fed an in-memory RDF/XML view.

**Common mistakes.** Putting sample patients in the ontology "for convenience", which makes the ontology unpublishable the day real data arrives. Letting data files declare new classes or properties, which silently changes the model. Treating a vocabulary concept as data (or a drug as schema). Validating the data file alone and being surprised it fails: SHACL needs the schema.

## 11. What this chapter does not claim

The merged graph is a runtime view; the project does not publish a single combined OWL file. The data header's `owl:imports` is documentation for readers and tools that resolve imports; this project resolves the import itself (by loading both files) rather than over HTTP, and strips it for the reasoner. The Neo4j load itself was not exercised against a live server.
